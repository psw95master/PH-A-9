**공유 규칙 문서는 한 벌을 셋이 쓰고, 기억은 기기마다 따로 둔다. 이 둘을 헷갈리지 않는다.** (260814 배선 확정)

## 규칙 문서 두 개

| 파일 | 적용 시점 |
|---|---|
| `STYLE.md` | **항상.** 페리에게 답하거나 페리에게 갈 산출물을 만드는 모든 순간 |
| `DESIGN.md` | **설계 작업일 때만.** 화면·플로우·프로토타입·UI |

1. 둘은 성격이 달라 **절대 병합하지 않는다.** STYLE 은 "어떻게 답하는가", DESIGN 은 "어떻게 설계하는가"다.
2. 베리티(클로드 앱)·팹(26맥)·세리(19맥) 셋이 **같은 내용**을 쓴다. 창구가 채팅이든 CLI 든 슬랙이든 동일하다.
3. 이름·소속·직무는 이 문서들이 다루지 않는다. [[assistant-name]] 정본을 그대로 따른다.

## 어디에 있나 (260814 확인)

1. 서랍: `~/.claude/projects/-Users-psw95-projects/memory/00. PH-B-24. Memory of comm`
2. 심링크 대상: `~/.claude/agent-hub/PH-B-24. Memory of comm` — **이름이 둘이지만 파일은 한 벌**이다. 어느 쪽에서 고쳐도 같은 파일.
3. 실물 저장소: 깃허브 비공개 `psw95master/PH-A-9`
4. `~/.claude/CLAUDE.md` 가 두 파일을 직접 가리키므로 **매 세션 자동 적용**된다.

## 받아오기는 자동, 올리기는 수동

1. **받아오기** — 세션 시작 때 `rules-sync` 가 자동으로 최신을 내려받는다.
2. **올리기** — `rules-sync push "무엇을 왜 고쳤는지"` 로만 올린다. 실행 파일은 `~/.local/bin/rules-sync`.
3. **자동 커밋을 안 하는 이유**: 무엇이 왜 바뀌었는지 남기려고 깃을 골랐는데, 자동 커밋이 이력을 `auto: 날짜` 로 채우면 그 목적이 사라진다.
4. **규칙 문서에는 버전 파일(`_v1.0` 등)을 만들지 않는다.** 깃 이력이 그 역할을 한다. [[guide-file-versioning]] 의 "에이전트 규칙 문서는 버전 안 쌓음"과 같은 결론.

## 기억 사본은 반대 성질

1. 내 기억 사본은 같은 저장소의 `PH-B-27. Memory of Cerryde/` 로 올라간다. 팹 것은 `PH-B-25. Memory of PAB/`.
2. 사본 폴더는 **자동 커밋**이다 — "언제 이랬다"는 스냅샷이라 이유를 적을 성질이 아니다.
3. 내보내기 훅이 **26맥에만** 있어서 **팹 세션이 끝날 때** 밀린다. 내 쪽에서 밀 수 없다.
4. 사본을 고쳐도 내 기억은 안 바뀐다. 구글 드라이브 사본은 별개 경로다 — [[memory-copy-on-drive]].

**How to apply:**
1. 규칙을 고쳤으면 **반드시 이유를 적어 push** 한다. 안 그러면 팹은 모른다.
2. **팹의 메모리를 직접 고치지 않는다.** 반대도 마찬가지 — [[device-split-memory]].
3. 규칙이 최신인지 의심되면 `rules-sync` 를 한 번 돌려 확인한다. 최신이면 마지막 커밋 한 줄만 찍고 끝난다.
4. 사본이 밀렸다는 얘기가 나오면 내 소관이 아니다. 팹에게 넘긴다.
