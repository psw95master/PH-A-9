> 🚨 **이 경로를 기억에서 꺼내 쓰지 말 것.** 하루 만에 이름과 자리가 둘 다 바뀌었다 (`01. Project zip/…/LB-C-19` → `01. Project Hub/PH-A-9/PH-B-25`, 260813). 스크립트는 **경로가 아니라 폴더 이름**으로 찾고, 못 찾으면 소리내어 실패한다 — 그때 `cerry-export` 의 `PAB_DEST` 한 줄만 고치면 된다. 사본을 고쳐도 에이전트에는 반영되지 않는다 (폴더의 `README.md` 참고). 옛 구글 드라이브 사본(`A11-CRA-6_Pab Pab` / `A11-CRA-7_Cerry de`)은 폴더명 개편 중 사라져 이미 끊겨 있었고 260812에 걷어냈다. 출처: Notion `PSW R&R Guide` (**A20-B-21**), 작업 로그는 `A20-C-17_log_260729.md`.

**Why:** 260728까지는 두 맥이 iCloud 폴더 하나를 양방향으로 밀고 당겼다(`cerry-mem sync`). 목표는 "한 명의 연속된 비서"였지만, 같은 파일을 서로 다른 시점에 덮어쓰면서 충돌이 반복됐다 — `rsync -u` 는 mtime 으로 한쪽을 통째로 버리므로 병합이 아니라 손실이었다. 운영 규칙으로 덮을 수 없는 구조적 한계라, 공유를 없애는 쪽으로 방향을 틀었다. **한 파일에 쓰는 주체가 하나면 충돌은 일어날 수 없다.**

**철거한 것 (260729):**
- 26맥의 `memory` 심링크 → 로컬 실폴더로 전환. 옛 iCloud 공유 폴더는 내용을 두 곳으로 나눠 옮긴 뒤 **260729에 페리가 삭제했다.** 개편 직전 상태의 전체 백업은 `~/.claude/backups/rnr-split-260729-0235/` 에만 남아 있다.
- 양쪽 `settings.json` 의 `SessionStart`/`SessionEnd` → `cerry-mem sync` 훅 제거.
- `cerry-mem` 스크립트 자체를 양쪽에서 삭제. 남은 일이 스킬 전송뿐이라 **`cerry-skills`** 로 대체했다 (26맥 → 19맥 단방향, 그대로 유지).
- `cerry-links.tsv` 에서 `memory` 행 제거. `cerry-link` 는 심링크만 다루므로 이제 스킬 4개만 관리한다.

**새로 만든 것:** `cerry-export` (26맥 전용). 로컬 → **구글 드라이브** 단방향 (260813~). 되돌아오는 경로가 없어서 사본을 고쳐도 에이전트에 영향이 없고, 사본 폴더마다 그 사실을 적은 `README.md` 를 같이 심는다. 세리 쪽은 26맥에서 ssh 로 당겨와 내보낸다(19맥은 SSH 세션에서 클라우드 저장소를 못 읽는다 — [[reference-19mac-tcc-aqua-domain]]). `SessionEnd` 훅에 걸려 있다.

**목적지 이력: iCloud → 드라이브(260729) → 볼트(260812) → 둘 다 → 드라이브만(260813 확정).**

260812에 볼트로 옮긴 건 보기 품질 때문이었다 — 드라이브는 마크다운을 렌더하지 않아 `##`·`**` 가 그대로 보이고 `[[링크]]`도 죽는다. **그런데 그 판단이 틀렸다.**

**결정 기준은 렌더 품질이 아니라 URL 이 붙는지다. 노션이 허브이고 파일을 URL 로 등록해 관리하기 때문이다** ([[feedback-icloud-hub-architecture]]). 옵시디언 로컬 파일에는 대장에 붙일 URL 이 없다 (`obsidian://` 는 옵시디언 깔린 기기에서만 열려 대장용으로 못 쓴다). 페리는 마크다운 원문 읽는 데 불편이 없다고 확인해 주었다.

> **How to apply — 사본·산출물 자리를 정할 때 "노션 대장에 붙일 URL 이 나오는가"를 먼저 묻는다.** 보기 예쁜 것은 그다음이다. 이걸 안 물어서 260812~13에 볼트로 갔다가 하루 만에 되돌렸다.

볼트는 iCloud 안에 있지만 **사본이라 에이전트가 읽지 않으므로** iCloud 의 껍데기화·충돌 사본 위험이 운영에 닿지 않는다 (실물을 iCloud 에 두는 것과는 전혀 다른 얘기다).

> 실물을 클라우드에 두자는 안은 260812에 검토·기각. ①가상본(alias)은 셸이 1KB 바이너리로만 봐서 기억이 통째로 실종된다 ([[feedback-icloud-hub-architecture]]) ②드라이브 심링크는 19맥이 SSH·launchd 문맥에서 마운트를 못 읽어 세리가 기억을 잃는다 ③260728 양방향 충돌 사고의 조건이 되살아난다. **원본은 로컬, 사본만 클라우드.**

드라이브 마운트(`~/Library/CloudStorage/GoogleDrive-*`)는 19맥의 SSH·launchd 문맥에서는 못 읽지만, **26맥에서 Claude Code 의 자식으로 도는 훅은 GUI 세션을 물려받아 읽고 쓸 수 있다** (260729 실측). [[id-and-log-convention]] 의 "드라이브는 MCP 로만 접근" 규칙은 19맥 기준이며, 26맥 세션 문맥에는 해당하지 않는다. 옛 사본들의 백업: `~/.claude/backups/icloud-agent-260729/`, 스크립트 옛 버전은 `~/.local/bin/.cerry-export.bak-260812`.

**사본은 "거울"이지 "백업"이 아니다 — 260813에 페리가 그게 낫다고 판단했다.** `--delete` 라서 내가 지운 기억은 사본에서도 사라진다. 즉 하드웨어 사고는 막아주지만 잘못 지운 실수는 못 막는다(아이클라우드 "최근 삭제 항목"이 30일 받쳐줄 뿐). **버전을 쌓는 백업 방식을 다시 제안하지 말 것** — 항상 현재 상태와 일치하는 쪽이 낫다는 게 결론이다.

**How to apply:**
- **다른 맥의 메모리를 고치지 말 것.** 세리의 기억이 잘못됐으면 세리에게 말해야 한다. 19맥 파일을 ssh 로 직접 손대면 그게 예전 충돌의 재현이다.
  - **예외: 페리가 명시적으로 시키면 한다** (260730 선례 — 이름 규칙 오류를 팹이 ssh 로 직접 고쳤다). 순서는 ①19맥에 도는 claude 세션·tmux 확인 → ②`~/.claude/backups/` 에 원본 백업 → ③`scp` 로 교체 → ④검증. 고친 뒤 **켜져 있던 세션은 반드시 다시 열어야** 반영된다 — 메모리는 세션 시작 때만 읽힌다.
  - 19맥의 슬랙 봇은 `claude` 를 홈(`/Users/psw95`)에서 띄우므로 **CLI 와 같은 메모리 한 벌을 본다** (260730 확인). 한쪽만 고치는 일은 없다.
- 메모리를 쓸 때 **이 기기에서만 참인 내용을 마음껏 써도 된다.** 예전 규칙("어느 맥에서든 참인 것만 쓸 것")은 폐기됐다.
- `settings.json` 은 여전히 기기별 로컬 파일이고 이제 훅 구성도 서로 다르다 — 26맥만 `cerry-guard` + `cerry-export` 를 돌린다 ([[reference-settings-json-not-synced]]).
- 스킬은 예외로 계속 공유한다. 26맥/iCloud 에서 만들고 `cerry-skills` 로 19맥에 내려보낸다 ([[skill-registration-routine]]).
