# PH-B-24. Memory of comm — 공용 규칙

> ⚠️ **여기는 사본이 아니라 실물입니다.** 형제 폴더(`PH-B-25`·`PH-B-27`)는 자동으로 만들어지는 읽기 전용 사본이지만, 이 폴더는 다릅니다. **여기 있는 파일을 고치면 실제로 적용됩니다.**

## 무엇이 들어 있나

| 파일 | 언제 적용되나 |
|---|---|
| `STYLE.md` | **항상.** 페리에게 답하거나 페리에게 전달될 산출물을 만드는 모든 순간 |
| `DESIGN.md` | **설계 작업일 때만.** 화면·플로우·프로토타입·UI 를 만들 때 |

## 누가 쓰나

베리티(클로드 앱) · 팹(26맥) · 세리(19맥) **셋이 같은 내용을 씁니다.** 창구가 채팅이든 CLI 든 슬랙이든 동일합니다.

각 맥에서는 메모리 폴더 안에 서랍처럼 보입니다.

```
memory/00. PH-B-24. Memory of comm  →(심링크)→  ~/.claude/agent-hub/PH-B-24. Memory of comm
```

이름이 둘이지만 **파일은 한 벌**입니다. 어느 쪽에서 고쳐도 같은 파일입니다.

## 고친 내용이 반영되는 방법

1. **받아오기는 자동입니다.** 각 세션이 시작될 때 `rules-sync` 가 최신을 내려받습니다. 한쪽 맥에서 고쳐 올리면 다른 쪽은 다음 세션부터 그 규칙으로 답합니다.
2. **올리기는 수동입니다.** `rules-sync push "무엇을 왜 고쳤는지"` 로 올립니다.

올리기를 자동으로 하지 않는 이유는, **무엇이 왜 바뀌었는지를 남기려고** 깃을 골랐기 때문입니다. 자동 커밋은 그 이력을 `auto: 날짜` 로 채워 목적을 없앱니다. (메모리 사본 폴더는 반대로 자동 커밋입니다 — 그쪽은 "언제 이랬다"는 스냅샷이라 이유를 적을 성질이 아닙니다.)

## 고칠 때 지킬 것

1. **`STYLE.md` 와 `DESIGN.md` 를 합치지 마세요.** STYLE 은 "어떻게 답하는가", DESIGN 은 "어떻게 설계하는가"입니다. 성격이 달라 섞으면 유지보수가 헝클어집니다.
2. **파일 맨 위 `---` 로 감싼 머리말을 지우지 마세요.** 메모리 목차가 그 `description` 을 읽어 요약을 만듭니다. 지우면 목차에 *(요약 없음)* 으로 나옵니다.
3. **판단·결정에는 날짜를 남기세요.** `260814 확정` 형식입니다.
4. **버전 파일(`_v1.0`, `_v1.1`)을 만들지 마세요.** 깃 이력이 그 역할을 합니다. 260814에 확정된 규칙입니다.
