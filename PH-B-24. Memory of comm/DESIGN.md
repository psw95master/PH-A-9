# 디자인·프로토타입 원칙

> **적용 시점**: 화면·플로우·프로토타입·UI 컴포넌트를 설계하거나 만드는 순간.
> 답변 방식·문장 톤은 이 문서가 다루지 않는다. `STYLE.md`를 따른다.
> 갱신 이력은 드라이브 버전 파일(`DESIGN_v1.0.md`…)로 관리한다.

---

## 01. 콘텐츠
1. 더미 텍스트(lorem ipsum) 금지. 실제 맥락의 카피로 채운다.
2. 카피를 지어내야 할 때는 지어냈다고 표시한다. (`※임시 카피`)
3. 숫자·날짜·이름도 그럴듯한 실제 값으로 채운다. `홍길동`, `000-0000` 같은 자리표시자를 남기지 않는다.

## 02. 화면 범위
1. 해피 패스만 만들지 않는다. **빈 상태 / 로딩 / 에러 / 첫 진입**을 함께 포함한다.
2. 모바일 우선으로 잡고 데스크톱을 파생시킨다.
3. 스크롤이 긴 화면은 첫 화면(스크롤 전)에서 무엇이 보이는지 먼저 정한다.

## 03. 시각 원칙
1. 타이포와 여백으로 위계를 먼저 잡는다. 장식은 마지막에.
2. 색으로만 정보를 구분하지 않는다. 형태·위치·라벨을 함께 쓴다.
3. 기본형이 템플릿처럼 보이지 않게 한다. 기성 UI 킷의 기본값을 그대로 쓰지 않는다.
4. 폰트·색·간격은 값을 고정해 토큰으로 정리한다. 화면마다 임의로 바꾸지 않는다.

## 04. 코드 인계 대비
1. 컴포넌트·변수 네이밍은 영문으로 통일한다.
2. 같은 역할의 요소는 같은 이름을 쓴다. 화면별로 이름이 갈리지 않게 한다.
3. 상태(state)가 있는 컴포넌트는 상태 목록을 함께 적는다. (default / hover / active / disabled 등)
4. 인터랙션은 "무엇을 누르면 어디로"까지 명시한다. 화면만 던지지 않는다.

## 05. 산출 시 함께 남길 것
1. 결정한 안뿐 아니라 **검토했다가 버린 대안과 그 이유**.
2. 미확정 항목은 `※확인 필요`로 남긴다. 임의로 채우지 않는다.
3. 판단·결정에는 날짜를 남긴다. (`260814 확정` 형식)
